# RJ NETWORK V2.2 — Deployment Checklist

## 1. Create D1

Create a Cloudflare D1 database named `rj-network`, then put the generated database ID in `worker/wrangler.toml`.

## 2. Apply schema

From `worker/`:

```bash
wrangler d1 execute rj-network --remote --file=schema.sql
```

## 3. Set secrets

```bash
wrangler secret put ADMIN_API_KEY
```

Recommended before public ticket creation:

```bash
wrangler secret put TURNSTILE_SECRET_KEY
```

Optional Telegram notifications:

```bash
wrangler secret put TELEGRAM_BOT_TOKEN
wrangler secret put TELEGRAM_CHAT_ID
```

## 4. Deploy Worker

```bash
wrangler deploy
```

Copy the Worker URL, for example `https://rj-network-v2-api.<subdomain>.workers.dev`.

## 5. Connect the GitHub Pages site

Open browser DevTools on the RJ NETWORK site and run once:

```js
localStorage.setItem('rj_api_base','https://YOUR-WORKER-URL')
```

For a permanent deployment, replace the empty default in `assets/api.js` with the production Worker URL, commit, and push.

## 6. Turnstile

The Worker supports Turnstile verification when `TURNSTILE_SECRET_KEY` is present. The public support form still needs the matching Turnstile widget/site key added before enforcing it. Do not add the secret key to frontend code.

## 7. Admin

Use `admin.html` over HTTPS. Enter the Worker URL and Admin API Key. The page keeps the key only in JavaScript memory for the current tab and does not write it to localStorage.

## 8. Production hardening

- Restrict `ALLOWED_ORIGINS` to the real RJ NETWORK origin only.
- Add Cloudflare WAF/rate limiting to `/api/tickets`.
- Enable Turnstile before broad public use.
- Keep `ADMIN_API_KEY` in Worker secrets only.
- Use a custom API subdomain such as `api.rjnetwork...` once DNS is ready.
- Back up D1 and test restore procedures.
