# RJ NETWORK V2.5 — Billing & Payment System

V2.5 adds invoice, payment-submission, verification and billing ledger functionality on top of V2.4.

## What is included

- Customer invoices with one invoice per customer/month.
- Invoice states: unpaid, pending, paid, overdue, void.
- Customer payment history.
- Customer payment submission using bKash/cash/bank/other.
- Manual admin verification: approve/reject/refund workflow.
- Partial payment support; invoice becomes `paid` when approved payments reach invoice amount.
- Billing events for audit history.
- Admin billing statistics.
- Admin invoice generation.
- Admin payment verification page: `billing.html`.
- Customer portal billing/payment section in `customer.html`.

## Important payment model

This release does **not** automatically verify bKash transactions. Customer-submitted payments remain `pending` until an authorized admin verifies them. No payment gateway credentials are embedded in frontend code.

The current customer-facing bKash instruction uses the RJ NETWORK payment number already used by the project: `01714-019016` (Personal / Send Money).

## Database migration

For an existing V2.4 D1 database, run:

```bash
npx wrangler d1 execute rj-network --remote --file=worker/V2.5-MIGRATION.sql
```

For a fresh database, use the updated `worker/schema.sql`.

## API endpoints

Customer authenticated:

- `GET /api/customer/invoices`
- `GET /api/customer/payments`
- `POST /api/customer/payments`

Admin authenticated:

- `GET /api/admin/invoices`
- `POST /api/admin/invoices`
- `GET /api/admin/payments`
- `PATCH /api/admin/payments/:id`
- `GET /api/admin/billing-stats`

## Deployment sequence

1. Apply V2.5 migration to the existing D1 database.
2. Deploy the updated Worker.
3. Confirm `GET /api/health` responds with `RJ NETWORK V2.5 API`.
4. Set the same Worker URL in `assets/config.js`.
5. Open `admin.html` and confirm the **Billing** link opens `billing.html`.
6. Create a test customer invoice.
7. Login to `customer.html` and submit a test payment.
8. Verify the payment from `billing.html`.
9. Confirm the invoice changes to `paid` when the approved amount reaches the invoice total.

## Security notes

- Customer billing endpoints require the existing customer session token.
- Admin billing endpoints require the existing `ADMIN_API_KEY` Worker secret.
- Payment amounts are checked server-side against the remaining invoice balance.
- Customer cannot submit a payment for another customer's invoice.
- Payment approval is an admin action; do not expose the Admin API key publicly.
